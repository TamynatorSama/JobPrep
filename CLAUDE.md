# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Platform

Windows-only. The bundled audio recorder uses WASAPI (the `wasapi` crate), credentials live in Windows Credential Manager via `keyring`, and the sidecar uses `taskkill /T /F` to clean up the Python process tree. Develop and test from PowerShell on Windows.

## Common commands

```powershell
# Frontend (React + Vite, runs at http://localhost:1420)
npm install
npm run dev                 # Vite dev server only — no Tauri runtime
npm run build               # tsc --noEmit + vite build into ./dist

# Full app (frontend + Rust shell + Python sidecar)
npm run tauri:dev           # Tauri auto-starts `npm run dev` per tauri.conf.json
npm run tauri:build         # production bundle

# Python backend (run once)
cd backend
.\setup.ps1                 # creates .venv (Python 3.11/3.12), installs deps + research_scraper engine from a sibling checkout

# Rust (from src-tauri/)
cargo check                 # fast type-check — preferred for quick iteration
cargo clippy
cargo fmt
```

Tests: Rust unit tests only — `cargo test --lib` from `src-tauri/` (ai_routing, chatgpt_auth, vad, copilot_listen, voice_audio). No `pytest` config, no Vitest. `backend/test_research.py` is an ad-hoc script, not pytest.

Measurement: `backend/bench/latency_harness.py` spawns its own sidecar and times boot, speech (Piper → `/voice/stt`, with WER) and copilot answers (TTFT, total, tokens via `/metrics/usage`) on 20 fixed interview questions with your real job context. `--skip-llm` = no API spend; `--model <id>` pins a model for A/B; `--pipeline` replays each question as audio, in real time, through the copilot's real Rust listening pipeline (`src-tauri/examples/copilot_replay.rs`: VAD → endpointing → streaming Whisper → answer) and reports interviewer-stops → first-token plus WER vs the batch `/voice/stt`. Reads keys from Credential Manager targets `<field>.InterPrep` (UTF-16 blobs — the Rust `keyring` layout, not Python keyring's). Results → `backend/bench/results/` (gitignored). `backend/bench/token_session.py` is the Phase 3 token gate: one scripted prep day on one job (job brief, 6 coach turns, manual cheatsheet, 10-turn mock interview, auto cheatsheet, 20 copilot answers, 1 JD extract) with payloads mirroring App.tsx, reporting input/cached/output/billed tokens per section; `bench/judge_session.py <old> <new>` blind-judges two runs' outputs (smart tier) for the "no worse" check — same-code runs swing ±3 of 20 copilot pairs, so read it against that noise. Baseline: `results/20261001-184340-baseline-session.json` (137,099 input tokens). `bench/screen_gate.py` is the Phase 4 gate: runs `src-tauri/examples/screen_probe.rs` (a coding problem window under a magenta window cloaked with `WDA_EXCLUDEFROMCAPTURE`, captured through `screen::capture_window`, plus an uncloaked control capture) against a live sidecar — overlay absent + p50 keypress → first token ≤ 2 s (measured 1.8 s on gemini-3.8-flash). `bench/tts_gate.py` is the Phase 5 gate (no API spend): spawns a sidecar, warms the copilot's Whisper, then per voice engine times cold `/voice/prepare` and `/voice/tts_stream` first PCM bytes on 20 unseen interviewer sentences (Kokoro rotates a 4-voice panel) plus nvidia-smi GPU memory per stage — Kokoro p50 ≤ Piper p50 and ≥ 1 GB GPU free (measured 114 vs 156 ms; sidecar +1,042 MiB, 3.6 GB free; `--vibe` adds VibeVoice). `bench/mac_speech_bench.py` (Phase 6 step 1 — Phase 6 was then stopped: the Mac kept up but would be slower than the PC and Piper-only; no Mac server exists) is self-contained (no repo imports) to run ON the 2017 Intel MacBook Pro: Piper first audio + Whisper tiny/base.en int8 and Moonshine tiny/base ONNX (WER, finalize, last-3 s tail) — `moonshine-voice` has no wheels below macOS 15 and onnxruntime 1.23.2 is the last with Intel-Mac wheels. `npm run build` also runs `scripts/check-copilot-stealth.mjs`, which fails on `title=` / `<select>` / `<datalist>` in `src/copilot` (browser popups escape the capture cloak — use `aria-label`).

Sidecar boot: routes import heavy deps lazily (langgraph in `routes/research.py`, `research_scraper` in `routes/company_research.py`, python-docx via `resume_docx.py` / `routes/docx_editor.py`), and `main.py` pre-imports them in a background thread after startup. Keep new heavy imports off module level — boot import went from ~10s to ~0.6s this way.

`src-tauri/src/main.rs` is a 7-line shim — there is no CLI surface left. The headless `--seconds` / `--list-devices` flags described in `README.md` and `AGENTS.md` no longer exist; the recorder is reachable only through the Tauri commands `list_audio_devices` / `start_recording` / `stop_recording`. ## Architecture

Three-tier desktop app: React UI → Tauri Rust shell (IPC + native services) → Python FastAPI sidecar (LLM + scraping). The crate name is `interprep`; the product is InterPrep, an AI interview-prep coach.

### Frontend — `src/` (React + TypeScript, single file)

`src/App.tsx` (~3.1k lines) holds the entire UI in one component tree with local React state. `src/styles.css` and the `T = { ... }` token block at the top of `App.tsx` carry the dark theme. Resume uploads parse PDF (`pdfjs-dist` worker URL imported via Vite's `?url` suffix), DOCX (`mammoth`), MD/TXT in-process before sending text to the backend.

All backend access goes through `invoke(...)` and `listen(...)` from `@tauri-apps/api` — there is no `fetch`/HTTP layer in the frontend.

### Rust shell — `src-tauri/src/`

`main.rs` → `lib.rs::run()` registers state and IPC handlers. Modules:

- **`sidecar.rs`** — spawns the Python FastAPI process (`uvicorn main:app`). Discovery order: `INTERPREP_BACKEND_DIR` env → walk up to 6 levels from `current_exe()` → walk up to 6 levels from `current_dir()` looking for `backend/main.py`. Python order: `backend/.venv/Scripts/python.exe` → bundled `python/python.exe` → `py -3.12` / `py -3.11` / `python3.x`. Polls `/health` for up to 30s; on `ExitRequested` runs `taskkill /T /F /PID <pid>` plus `Child::kill` to wipe the whole Python process tree.
- **`backend_client.rs`** — `reqwest::blocking` POSTs to `/{chat|research|company-research|application}` endpoints and forwards each SSE `data:` line to the frontend as a window event. SSE event types map to Tauri events: `token`→`chat:token`, `stage`→`chat:log`, `scorecard`→`chat:scorecard`, `resume_docx`→`chat:resume_docx`, `tailored_resume`→`chat:tailored_resume`, `done`→`chat:done`, `error`→`chat:error`. The frontend uses the same event channel for every workflow — there's no per-stream namespacing, so only one stream should run at a time.
- **`credentials.rs`** — Windows Credential Manager (`keyring` crate, service `"InterPrep"`). One entry per field. Empty value = delete entry. Fields: `llm_provider` (legacy toggle — now only the default for AI routing's first run) + per-provider API keys. Entries are stored under target `<field>.InterPrep` with UTF-16 blobs (keyring-rs layout). Legacy Glassdoor/Indeed + retired Groq/Ollama entries are deleted on save.
- **`ai_routing.rs`** — Settings → AI routing: "same" (one provider/model/fallback for everything, the default) or "per_feature" (copilot, coach, interview, resume_tailor, cheatsheet, role_fit, company_research, extension, embeddings). Saved to `%LOCALAPPDATA%\InterPrep\ai_routing.json`. **`llm_for(feature)` builds the snake_case `llm` payload for every backend request** (mirrors Python's `LLMConfig`: provider/model/keys + `feature`, `fallbacks`, `substituted_from`, `embeddings_provider`). Each Tauri command knows its feature and builds the payload itself — **the webview never sends `llm` or keys for AI calls** (the copilot window never loads credentials at all). Unconnected/unsupported choices get a stand-in provider (`substituted_from`), and fallback "" = first other connected provider. Embeddings resolve to `local` (the sidecar's on-device model; Settings shows "On-device") unless the per-feature Embeddings row names a provider. Answers from a stand-in/fallback arrive with a `route` SSE event → `chat:route` → "via X · fallback" badge (App bubbles via `ChatMsg.via`, overlay drag bar).
- **`chatgpt_auth.rs`** — Sign in with ChatGPT (OpenAI's open-source "ChatGPT plan usage" flow): routing provider `"chatgpt"` = OpenAI Responses API billed to the user's plan. Browser OIDC + PKCE against `auth.openai.com`, one-shot listener on `http://127.0.0.1:<port>/auth/callback`, first sign-in uses `client_id=dynamic_agent_client` + `agent_name_hint` and saves the issued `oaiapp_…` id, per-install `ext_agent_host_id` (`urn:uuid:`), requires the `chatgpt.tokens.use.direct` scope, verifies the ID token (RS256/JWKS, issuer, audience, nonce). Refresh token / client id / ID token / email in Credential Manager (`chatgpt_*` fields — not part of `Credentials`, never sent to the webview); 1h access token in memory, refreshed by a background thread that re-seeds the sidecar. Refresh tokens rotate — always save the new one. `"chatgpt"` can't run company research (Chat Completions engine) or embeddings. Python: plan models from `GET /v1/models` (`visibility:"list"`, tiered by name in `_plan_tiers`), `ChatOpenAI(use_responses_api=True, store=False, streaming=True)` wrapped in `_PlanChat`, which moves system messages into the Responses `instructions` field (verified on Plus: plan requests reject system messages AND `max_output_tokens` — never send an output cap; reasoning effort accepts none/low/medium/high, "low" on fast tiers). Plus TTFT measured 1.5–3.9 s vs ~0.5 s on Gemini Flash-Lite, hence the "everything except copilot" preset; plan-limit errors (`subscription_sharing_usage_*`) count as `provider_down` → next provider.
- **`jobs_store.rs`** / **`resume_store.rs`** — JSON files under `%LOCALAPPDATA%\InterPrep\` (`jobs.json`, `resumes.json`). Atomic write via temp-file + rename so a mid-write crash never corrupts the file.
- **`types.rs`** — `Job` / `ChatThread` / `ChatMsg` / `StageNote`. `serde(rename_all = "camelCase")` on `Job` for JS interop; IDs are `String` because the frontend mints them with `Date.now()`.
- **`copilot_listen.rs`** + **`vad.rs`** — the copilot's Rec session: one continuous system-audio capture (`voice_audio::capture_system_continuous`, which feeds silence when loopback stops sending packets) → `Resampler16k` → Silero v6 in-process via `ort` (model embedded from `src-tauri/models/silero_vad_v6.onnx`, ~0.1 ms/32 ms frame) → `Tracker` (pure, unit-tested endpointing: onset, `Pause` 160 ms, `Spec` 320 ms, `Final` 900 ms, `LongFinal` 1.8 s, `Commit` 2.2 s) → `Controller` thread, which streams 16 kHz PCM into a sidecar Whisper session (`/voice/asr/*`) and **starts the answer from Rust** (`AppSink` → `backend_client::stream_chat`, mode copilot). First endpoint per question is speculative; speech resuming cancels it (`backend_client::cancel_stream`) and the retry waits for `Final`. Events: `copilot:speech|partial|question|resume|commit|stopped`; the answer arrives as `chat:*` under the `streamId` from `copilot:question`. Commands `copilot_listen_start/stop`, `cancel_chat_stream`; Ctrl+` (`listen_finish`) forces an answer now. If the VAD can't load, the overlay falls back to the old `voice_listen_system` loop. Rust warms the recognizer (`/voice/asr/warm`) as soon as the sidecar is up.
- **`screen.rs`** — copilot screenshot → answer. Capture button (`copilot_capture`, adds to a stack of ≤ 3) or Ctrl+Shift+\ (`screen::hotkey`: capture + answer at once; if the overlay isn't built yet it captures first, builds it, and `copilot_screen_ready` starts the answer once the page is listening). Target = foreground window, or the last non-overlay foreground window (250 ms polling tracker) when the overlay has focus. GDI `BitBlt` of the window's DWM frame bounds — the overlay's `WDA_EXCLUDEFROMCAPTURE` keeps it out (not Windows Graphics Capture: yellow border) → WinRT `Windows.Media.Ocr` → WinRT `BitmapEncoder` JPEG (Fant scaling; native code, fast in debug builds). Text-heavy (≥ 200 OCR chars over ≥ 4 lines) sends a 768 px image + the OCR text, else 1,568 px. Images stay in Rust memory (never disk, the webview only gets 240 px previews) and are dropped once sent; `copilot_screen_answer` posts `/chat/stream` mode `screen` with `llm_for("copilot")`. Measured: capture + OCR + encode 60–170 ms.
- **`recorder.rs`** — unchanged WASAPI dual-stream backend (system audio via render-loopback + mic via capture, both written as 32-bit float WAV via `hound`). Each worker initializes COM (MTA) on its own thread via `ComGuard`; an `Arc<AtomicBool>` stop flag is shared so one worker's error trips the other. `save_resume_docx` decodes the base64 `.docx` from `chat:resume_docx` into `%APPDATA%\InterPrep\applications\<job_id>\resume.docx`.

### Python sidecar — `backend/` (FastAPI + LangGraph)

`main.py` mounts routers under `/chat`, `/research`, `/company-research`, `/application`, `/voice`, plus the token-guarded browser-extension bridge (`/config`, `/store`, `/autofill`, `/inbox`). Models in `models.py` (Pydantic).

**Multi-LLM:** every request carries an `llm: LLMConfig` payload (built per feature by Rust's `ai_routing::llm_for` from AI routing + Credential Manager). `routes_for(cfg, tier)` yields (provider, model) pairs — the chosen provider's candidates, then each fallback provider's — and streaming routes walk them, skipping a provider after an auth error and emitting `route_event` once a non-chosen provider produces the first token. `/models/registry|list|test` (`routes/model_catalog.py`) back the Settings model picker and speed test. `backend/llm_provider.py` is the factory all routes go through — `make_chat_model` (lazy-imports the LangChain partner package per provider; **caches built models** keyed by provider/model/tier/temperature/max_tokens/key-hash so calls reuse the open connection), `candidate_models(cfg, tier)` (`_MODELS` registry: "instant" = copilot, "fast" = chat/interviewer/utility, "mid", "smart"; preferred→fallback per provider — Gemini 2.5 is access-restricted for new accounts, so 3.x leads), per-model thinking control (`_gemini_thinking`: 2.5 → `thinking_budget=0`, 3.x Flash/Flash-Lite → `thinking_level` low/minimal on instant/fast; OpenAI reasoning models → `reasoning_effort="low"`, Claude non-Haiku → `effort="low"`), `generate_json`/`generate_raw` (one-shot + lenient parse), `content_text` (flattens block-list content from Anthropic/Gemini 3), `make_embeddings` (auto = on-device `local_embed.py`: bge-small-en-v1.5 int8 ONNX on CPU, ~3 ms/query, 34 MB fetched once into the HF cache and loaded at boot only if already cached; an explicit Embeddings row picks Gemini `gemini-embedding-001` / OpenAI, each a fallback for the other — Gemini's `text-embedding-004` 404s and had silently switched RAG off). **Always pass the right `tier` to `make_chat_model`** — it decides thinking/effort, so a smart-tier model built with the default `tier="fast"` gets its reasoning dialed down. **Token meter:** every call reports `usage_metadata` via `record_usage` (`[usage] feature=… model=… in= cached= out=` in sidecar.log), tagged by `FeatureTagMiddleware` in `main.py` (path prefix → feature; chat refines to `chat:<mode>`); totals at token-guarded `GET /metrics/usage`. Streaming routes fold chunk usage with `merge_usage`. **The module is named `llm_provider`, not `llm`, because the embedded `research_scraper` package ships its own top-level `llm` package — naming it `llm` shadows the engine's import and breaks company research.** Extension-bridge routes read the config from `runtime_config` (seeded via `POST /config/seed` on startup + Settings save).

Routes:

- **`routes/chat.py`** — coach mode and live `interviewer` mode on the fast tier (a live spoken interview can't afford the smart tier's ~9.5s time-to-first-token; `INTERPREP_INTERVIEWER_TIER=smart` restores the old behavior), plus `copilot` mode for the stealth overlay: `COPILOT_SYSTEM` (plain text, first person, one sentence per line, ~60–110 words; answer shape chosen by question type — narrative for "tell me about yourself", one story for behavioral, direct reasoning with no forced resume reference for technical, company-tied for motivation; a fixed "headline + 3 metric beats" format sounded generic and resume-dumped; technical terms kept but in short, plain, spoken sentences — no formal or stacked phrasing, per the user), "instant" tier, `COPILOT_MAX_TOKENS` runaway cap. The overlay sends the raw question; the format lives in the prompt. `/config/seed`'s warmup (`routes/bridge.py`) builds the exact cached copilot client (instant tier) and screen client (fast tier) so the first live answer reuses their connections — on the route in the seed's `warm` field (Rust sends `llm_for("copilot")`; the seed's `llm` is the extension's, which used to be warmed instead and left a first luna screen answer at 21 s); it re-warms only when that route changes. Streams via the factory model's `.astream(...)`; model fallback only happens before the first token, with a TTFT deadline and an auth-error short-circuit. **Job brief** (`backend/job_brief.py`): copilot and interviewer turns swap the full job context (JD 1.5k + dossier 6k + resume 8k chars, built once by App.tsx `fullJobContext`) for a ~3k-char fast-tier condensation, cached by hash(prompt + context) in memory and `job_briefs.json`; the interviewer's `INTERVIEW SETUP` block is split off first so all modes share one brief per job. Rust prefetches it (`POST /chat/brief`, copilot.rs, 2 s debounce on a real context change, and once when the sidecar comes up); a miss uses the old context and builds in the background (5-min backoff after a failed build). Copilot input ~3,420 → ~1,530 tokens/question. Retrieval is coach-only (k=4, 3,000 chars), rides in the **last user turn** (system + history stay cache-stable), and skips text the job context already quotes. `chat_context.py` keeps a **rolling** recap (previous recap + newly rolled-out turns, chained prefix-hash keys) and moves the older/recent boundary in 6-message steps when that keeps ≤ 3k extra chars verbatim. A client hang-up mid-stream (the copilot's cancelled speculative starts) is metered as an estimate under `<feature>:cancelled`. Mode **`screen`** (Phase 4): `SCREEN_SYSTEM` classifies the screen (coding → approach, complexity, one fenced code block; quiz → answer + one-line why; design; error; spoken question) on the **fast** tier, `SCREEN_MAX_TOKENS` 4,000, job brief as context; `ChatRequest.images` (base64) + `screen_text` (OCR) become one user turn of text + `image_url` data-URL blocks (`_screen_content`). The overlay renders ``` fences as code blocks (`AnswerText` in Copilot.tsx).
- **`routes/research.py`** — JD-only role-fit analysis. LangGraph workflow defined in `agents/workflow.py` with nodes `extract → questions → tips`. Stage banners emitted on `on_chain_start`; tokens forwarded from `on_chat_model_stream`.
- **`routes/company_research.py`** — backed by the embedded `research_scraper` engine (editable-installed from `D:\code\ML\research_scraper`; LangGraph plan → search → scrape → reflect → peer → audit → synthesize, HTTP/JSON scraping — no browser, no logins). The engine's LLM router speaks the OpenAI-compatible wire format with a built-in fallback chain; the route maps the selected provider (gemini | openai | anthropic) onto the custom lane via the engine's `runtime.overrides` contextvar (Anthropic rides its OpenAI-compat endpoint `https://api.anthropic.com/v1`) and passes the spare gemini key as a fallback lane. The Gemini key also powers the Google Search grounding source regardless of provider.
- **`routes/inbox.py`** — extension job capture + `/inbox/extract` (fast tier on page text with repeated short lines dropped and a 12k-char window from just above the title; the extension tries JSON-LD first).
- **`routes/application.py`** — smart-tier resume tailor: aggregates evidence across master resumes, builds an ATS-tailored `.docx` (via `python-docx`, rendered in `backend/resume_docx.py`), streams the cover letter as tokens, and emits a scorecard JSON event. Also serves `/application/knockout-screen` for recruiter-style screen simulation.
- **`routes/voice.py`** — one speech engine layer (Phase 5; the Phase 6 Mac server serves the same contract). **TTS registry `_TTS`**: every voice has `available()` (find_spec only) / `load(speakers)` → sample rate / `warm(speakers)` / `stream(text, speaker)` → PCM16 frames; `_resolve_engine` swaps in Piper when the chosen engine is missing or failed (`tts_errors`, retried on the next `/voice/prepare`), and `/voice/tts_stream` reports the engine that spoke in `X-Engine`. Engines: **Kokoro-82M** (`kokoro` + `misaki[en]`/spaCy, torch on CUDA, 24 kHz, six US voices `KOKORO_VOICES` for the panel; model + voices load from the HF cache by path, no network; default when installed AND a GPU is present — on this CPU it's 0.6–1.9 s a sentence), **Piper** (onnxruntime CPU; the fallback; `_get_piper` must not import torch), **VibeVoice** (`vibe-rt`, opt-in). Measured on the RTX 4050: Kokoro first audio p50 114 ms vs Piper 156 ms, +792 MiB GPU; its cold start (torch + kokoro + spaCy imports ≈ 70 s, more with a cold disk cache) lands behind the mock-interview modal — App.tsx fires `voice_warm` when that modal opens and `/voice/prepare` joins it (per-engine `_warm_locks`). The engine string comes from Settings → Voice (`interprep.ttsEngine` in localStorage, "" = the sidecar's `default_engine`) via `voice_set_engine`; Rust passes it through untouched. **Recognizer registry `_ASR`** (`whisper`, `moonshine`): `open / push / finish / cancel`, one session table; `/voice/asr/start {engine}` (no body = Whisper, as Rust calls it), `/asr/chunk`, `/asr/snapshot` (Whisper only), `/asr/finish`, `/asr/close`; `/voice/stt-stream/*` stays as the Moonshine spelling the mock mic uses. Parakeet TDT 0.6B (onnx-asr, int8 CPU) was evaluated for the mock mic and dropped: 2.9% WER but 1.3 s to finalize, vs GPU Whisper 2.5% / 0.17 s and Moonshine 6.9% / 0.05 s. **Build rule:** torch TTS models are constructed under `_torch_build_lock` — transformers' `from_pretrained` (VibeVoice) switches torch to meta-device init process-wide, so a Kokoro `KModel` built concurrently got 688 empty meta params, failed, and Piper spoke instead (seen live after switching voices). A Piper fallback now raises an alert at interview start. `bench/voice_samples.py` writes the same 4-sentence reply in every engine/voice to `bench/results/voice-samples/` for listening tests. **cuDNN rule:** `_pin_torch_cudnn()` (idempotent, locked) must run before ANY ctranslate2 / faster_whisper import — `_stt_device`, `_get_stt`, `_vad_tail` all call it; a `/voice/status` poll that imported ctranslate2 mid-warm let its lone `cudnn64_9.dll` win and Kokoro's first synth then killed the sidecar ("Could not load symbol cudnnGetLibConfig"). Batch STT `/voice/stt`, Moonshine streams for the mock-interview mic, and the copilot's **streaming Whisper sessions** `/voice/asr/{warm,start,chunk,snapshot,close}`: raw 16 kHz PCM16 in, background re-decodes for partials, a decode on Rust's pause hint, and `snapshot(upto_samples)` that reuses any decode covering the last voiced sample (≈6 ms when it hits). All faster-whisper calls share `_stt_infer_lock`. A warm base.en decode is ~60 ms on the RTX 4050; a cold first load is ~1 min (ctranslate2/cuDNN DLL loading), hence the warm at sidecar start. `_get_stt` must not import torch: `_pin_torch_cudnn` locates torch's cuDNN via `find_spec` and `_stt_device` asks ctranslate2. `/voice/status` reports `stt_phase` (idle/loading/loaded/warming/ready/error).
- **`routes/cheatsheet.py`** — `POST /cheatsheet/build` (non-streaming JSON, smart tier). Aggregates a job's JD + resume + company-research dossier + conversation transcripts into a structured cheatsheet (`stories`/`facts`/`questions` via `generate_json`) and assembles the persisted markdown deterministically from those fields. Drives the copilot's Cheatsheet tab; rebuilt on a manual refresh (full) and automatically after a mock interview (`incremental`: the response's `seen` map — chars read per chat id — lets the next build send only the previous sheet + conversation text added since, no JD/resume/research; nothing new = no call; mock-interviewer lines are treated as practice signal, not company facts). The live cheatsheet rides to the overlay through the copilot context bridge (`set_copilot_context` carries it alongside the job context).

- `%LOCALAPPDATA%\InterPrep\resumes.json` — master resume library
- `%LOCALAPPDATA%\InterPrep\sidecar.log` — uvicorn stdout/stderr (single source of truth for sidecar boot failures). Written as UTF-8 because sidecar.rs sets `PYTHONIOENCODING=utf-8`; without it a `print` with `—`/`→` raises mid-request (cp1252)
- `%LOCALAPPDATA%\InterPrep\job_briefs.json` — condensed job briefs (LRU 24); `rag_cache\embeddings.json` — RAG chunk vectors by model namespace + content hash
- `~\.cache\huggingface\hub\models--hexgrad--Kokoro-82M` — Kokoro weights (~330 MB) + voice packs (fetched by `setup.ps1 -Voice` or on first use); Piper's voice in `backend\models\piper\` or `%LOCALAPPDATA%\InterPrep\voice\`
- `%APPDATA%\InterPrep\applications\<job_id>\resume.docx` — generated tailored resumes
- `%APPDATA%\InterPrep\applications\<job_id>\cheatsheet.md` — the job's living interview cheatsheet (also stored structured on the Job in `jobs.json`)

## Things that will trip you up

- **Don't add `fetch` calls from the frontend.** All backend traffic is `invoke` → Rust → `reqwest` to the sidecar. Adding direct HTTP from React breaks the SSE-to-Tauri-event bridge and the sidecar shutdown contract.
- **Sidecar discovery walks `current_exe()` first, then `current_dir()`.** In `tauri dev`, cargo runs from `src-tauri/`, so `./backend` doesn't exist — the walk-up from the cwd is what finds it. Don't simplify either branch without checking both `cargo run` and `npm run tauri:dev`.
- **Killing the sidecar requires `taskkill /T /F`, not `Child::kill`.** On Windows `Child::kill` only terminates the immediate process; anything the interpreter spawned is orphaned. The `ExitRequested` handler in `lib.rs` runs before Tauri tears down — that's the only reliable window to clean up.
- **SSE events use one global channel (`chat:*`).** Two concurrent streams will interleave tokens into the same listener. The UI must single-flight streams; don't kick off a second one before `chat:done` fires.
- **COM (MTA) must be initialized per-thread before any WASAPI call.** `query_device_catalog` deliberately runs on a fresh thread so its COM init doesn't poison the caller. Preserve that pattern.
- **Recorder writes 32-bit float WAV regardless of native device format.** `write_packet_as_f32` and `make_wav_spec` in `recorder.rs` are tightly coupled — change the spec, change the writer.
- **Python 3.13/3.14 are not supported.** Some LangChain / ML wheels lag. `backend/setup.ps1` enforces 3.11/3.12; the Rust `find_python` fallback list matches.
- **CORS is wide open (`allow_origins=["*"]`) in `backend/main.py`.** Fine because the sidecar binds to `127.0.0.1` only and is launched as a child of the Tauri shell. Don't expose the port externally.
- **`src/App.tsx` and `src-tauri/src/lib.rs` use CRLF line endings** (most other files are LF, `core.autocrlf` is off). `sed -i` from Git Bash rewrites a whole file to LF — a 10k-line diff. Edit them with the Edit tool, or restore CRLF afterwards.
- **`README.md` and `AGENTS.md` are stale.** They describe a pre-Tauri, egui-based recorder with a CLI. Treat this file as the source of truth; update the others if you touch anything they describe.
